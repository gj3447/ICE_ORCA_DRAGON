## 1. Overview

**APT** stands for **Anchor-Pyramid-Twin** development methodology. It is a semantic-layer methodology for AI-agent-driven software development where every concept lives in a Neo4j Knowledge Graph as the canonical source of truth.

APT governs how a project descends from abstract intent to concrete source code through four strictly ordered semantic worlds, using recursive span decomposition, crystallization to contracts, and TDD-based realization.

## 3. The Four Worlds (4 Semantic Layers)

### 3.1 SA (SemanticAnchor) World
- **Node:** `SA_World` / `APT_Layer_SemanticAnchor`
- **Definition:** Project-level identity anchor. Exactly 1 per project in the KG. The semantic anchor from which all recursive decomposition begins.
- **Purpose:** Fixes the project's reason for existence, domain, target part, and customer. All subsequent descent uses SA as the reference point.
- **Key rule:** SA is NOT a Span. It is the starting point that ENABLES the SP world.

### 3.2 SP (SemanticPyramid) World
- **Node:** `SP_World` / `APT_Layer_SemanticPyramid`
- **Definition:** A single world containing Spans (planning units) arranged in layers (L1 -> L2 -> ... -> Ln). Depth is unlimited, scaling with project complexity.
- **Key properties:**
  - SP is ONE world. There are not "multiple SPs." There are multiple Spans INSIDE SP.
  - Spans are graph nodes, not necessarily a tree. The key invariant is that layers exist.
  - DECOMPOSES_TO is N:N -- multiple parent Spans can decompose to multiple child Spans.
  - Same-layer Spans are fully parallel (zero mutual dependency).
  - Context window occupies exactly 2 layers (parent + child) at a time.
  - Child Spans are generated by weaving together multiple parent Spans + external KG knowledge (like a spider web).
  - External knowledge (design patterns, tech stacks, domain concepts, axioms, reference docs) connects to Span nodes via graph relationships. Higher link density = better decomposition quality.

### 3.3 ST (SemanticTwin) World
- **Node:** `ST_World` / `APT_Layer_SemanticTwin`
- **Definition:** The specification space where crystallized specifications live. Each SemanticTwin = Contract (I/O specification) + Task (TDD completion criteria).
- **Key rule:** ST is NOT code. It is "what to build," not "how to build it."
- **Contract properties:** input_type, output_type, pre_condition, post_condition, acceptance_test
- **Task properties:** AcceptanceCriteria that must PASS for Contract fulfillment

### 3.4 SCW (SourceCodeWorld)
- **Node:** `SCW_World` / `APT_Layer_SourceCodeWorld`
- **Definition:** The actual code files in the project directory that implement ST's Contracts.
- **Key rule:** Agent/developer vibe-codes/TDDs until Task's AcceptanceCriteria PASS.
- **Relationship:** Contract -[:MATERIALIZES]-> SourceCodeNode

### 3.5 Crystallization Frontier (SP <-> ST boundary)
- **Node:** `APT_Layer_CrystallizationFrontier`
- **Definition:** The named boundary between SP and ST worlds. When an AtomicSpan (a leaf Span that cannot be further decomposed) satisfies the 4 crystallization criteria, it crosses this frontier and becomes an ST.
- **This is the ONLY crossing point between SP and ST.** No other path exists.

## 4. The Six Operational Phases

### PH1: SemanticAnchor Alignment
Fix the SA. Register the project's reason for existence, domain, target part, and customer in the KG.

### PH2: RootIntentSpan Establishment
Derive the top-level intent span from SA. Define the entire project scope as a single root span and fix it as the SP world's topmost Span.

### PH3: SemanticPyramid Recursive Descent
Recursively decompose RootIntentSpan into L2 -> L3 -> ... spans. Each span has description, module_id, and parent relationships. When a span's 4 crystallization criteria are satisfied, it has reached the Crystallization Frontier.

### PH4: SemanticTwin Crystallization
For each frontier-reaching span, author a SemanticTwin: shared Contract (specification surface) + SemanticTask (execution unit). Contract has input_spec, output_spec, acceptance_criteria. SemanticTask defines specific execution scenarios.

### PH5: SourceCodeWorld Implementation
Realize PH4's Contract + SemanticTask as source code. TDD operates HERE: write tests from Contract's acceptance_criteria first, then implement code to pass them.

### PH6: KG/Runtime Feedback
Reflect implementation results back to the KG. Discoveries during implementation (new spans needed, contract modifications, task additions) are uploaded to KG. Return to PH3 or PH4 as needed. Bottom-up flow also operates here.

### Transition Rules
- **PH3 -> PH4 (ST Crystallization Rule):** When SP frontier is reached, create Contract + SemanticTask in KG for each leaf span.
- **PH4 -> PH5 (TDD Contract Realization Rule):** After Contract + SemanticTask are confirmed in KG, implement via TDD in SourceCodeWorld.

## 5. Core Axioms

### 5.1 Three Core Axioms (AptCoreAxiom)

| Axiom | Description |
|-------|-------------|
| **CoreAxiom_ContractOnlyAtST** | Contracts exist ONLY at ST. Spans do NOT have Contracts. Spans have only description/purpose. Contracts are created only when a leaf Span crystallizes to ST. |
| **CoreAxiom_InfiniteRecursion** | Span structure is infinitely recursive. No depth limit. Stops and crystallizes to ST only when completion conditions (primitive/value-judgment/atomicity) are met. The entire SP is the result of this infinite recursion. |
| **CoreAxiom_VerticalSubordination_HorizontalParallelism** | Vertical (parent->child) = N:N subordination. Horizontal (same-layer siblings) = fully independent. The reason for layer separation = parallel sub-agent accelerated development. Sibling dependency = decomposition error -> must re-decompose. |

### 5.2 Extended Axioms (AptAxiom)

| Axiom | Description |
|-------|-------------|
| **Axiom_MacroFlowIsSemanticAnchorToSemanticPyramidToSemanticTwinToSourceCode** | The canonical grand flow is SA -> SP -> ST -> SCW. Span, Contract, Task are NOT separate higher-level stages outside this flow; they are detailed operational elements placed INSIDE this flow. |
| **Axiom_UpperSpanIsAbstractMeaningLayer** | Upper spans are NOT actual source code files or runtime objects. They are abstract meaning layers that capture WHAT the source code and architecture structure MEAN. |
| **Axiom_SpanShouldDenselyLinkToExistingKnowledgeBeforeContract** | At the Span stage, increase connection density to existing KG knowledge, external methodologies, and domain concepts to enrich meaning, THEN crystallize to contract. |
| **Axiom_SpanExternalLinkDensityImprovesDescentQuality** | The higher the external knowledge link density of a Span (design patterns, domain concepts, tech stacks, etc.), the higher the semantic stability and reconstructability of top-down decomposition (DECOMPOSES_TO). Richer KG knowledge = stronger Span abstraction capability. |
| **Axiom_ContractDescentTargetsSingleFileProjectionNearContextWindow** | When entering SemanticTwin authoring and an explicit Contract is secured, the resulting source code realization should target a single small file or an adjacent implementation boundary that safely fits within the context window. |
| **Axiom_BottomUpAscentMapsSourceCodeMeaningBackToArchitecture** | In bottom-up ascent, source code meaning must be restored -- reconstructing contracts, spans, and architecture up to the semantic anchor. |

## 6. Span Decomposition Rules

### 6.1 DECOMPOSES_TO Relationship
- **Type:** N:N (many parents to many children, many children to many parents)
- **Direction:** Upper-layer Span -> Lower-layer Span
- **Context window:** Always occupies exactly 2 layers (parent layer + child layer)
- **Creation process:** Weave together multiple parent Spans + external KG knowledge dependencies to create child Spans
- **Provenance:** Track creation references via INFORMED_BY relationship

### 6.2 When to Split (Decomposition Criteria)
- A Span should be split when it cannot satisfy the 4 crystallization criteria
- Upper Spans are plans for creating lower Spans -- nothing more, nothing less (SpanPlanningNature constraint)
- Minimum branching factor: 2 (no upper limit) -- BranchingInvariant constraint

### 6.3 MECE and Completeness
- Same-layer Spans must be fully independent (zero mutual dependency)
- If sibling Spans depend on each other, that is a decomposition error requiring re-decomposition
- All decomposition paths must reach an AtomicSpan in finite steps (TerminationGuarantee)

### 6.4 Depth Rules
- Depth is the hop count from SA -- nothing more (DepthInvariant)
- Atomic and non-atomic Spans can coexist at the same depth
- L*_ name prefixes are legacy identifiers reflecting creation-time depth; they have no semantic meaning (NamePrefixCaveat)
- L3 being the AtomicSpan layer in one project is just that project's decomposition stopping at L3. Other projects may stop at L2 or go down to L7.

### 6.5 AtomicSpan vs LeafSpan
- **LeafSpan** = "a Span currently without child DECOMPOSES_TO." It is a state; it CAN be further decomposed if needed.
- **AtomicSpan** = "a Span judged to need no further decomposition." Must satisfy all 4 crystallization criteria.
- Not all LeafSpans are AtomicSpans.

### 6.6 Span Structure
- Spans are NOT necessarily a tree. They are a layered graph.
- The key invariant is that layers (L1, L2, ..., Ln) exist.
- External knowledge (design patterns, tech stacks, domain concepts, axioms) connect to Spans as graph relationships.

## 7. Crystallization Criteria (SP -> ST Transition)

An AtomicSpan crosses the Crystallization Frontier when ALL FOUR criteria are satisfied:

| # | Criterion | Question | Node Name |
|---|-----------|----------|-----------|
| 1 | **Type Expressibility** (OutputContractExpressible) | Can the OutputContract be expressed as a single type signature? | `OutputContractExpressible` |
| 2 | **Semantic Completeness** (TypeCapturesFullMeaning) | Does the type capture the full meaning losslessly? | `TypeCapturesFullMeaning` |
| 3 | **Implementation Feasibility** (CanWriteFunctionNow) | Can you write the function right now? | `CanWriteFunctionNow` |
| 4 | **Test Feasibility** (CanWriteAcceptanceCriteria) | Can you write the AcceptanceCriteriaFunction right now? | `CanWriteAcceptanceCriteria` |

If any criterion fails, the Span needs further decomposition (stay in SP world).

## 8. Contract Rules (at ST only)

### 8.1 Contract Properties
A fully specified Contract should contain:
- **input_type:** Input data type specification (typed signature)
- **output_type:** Output data type specification (typed signature)
- **pre_condition:** Preconditions that must hold before execution
- **post_condition:** Postconditions guaranteed after execution
- **acceptance_test:** Concrete test scenarios that validate correct implementation

### 8.2 Contract Example (fully typed)
**CT_Q1_NumpyTransfer:**
- **input_type:** `Sender: Zivid frame -> copy_data() -> xyz:float32[H,W,3], snr:float32[H,W], rgba:uint8[H,W,4]`
- **output_type:** `WS protocol: (1)JSON numpy_transfer_start{metadata{channels[{name,shape,dtype}],compression,raw_size}} (2)binary lz4.frame.compress(concatenated_arrays) (3)JSON numpy_transfer_end{capture_id,compressed_size,ratio}`
- **acceptance_test:** `AT1: xyz float32[H,W,3] roundtrip lossless. AT2: snr float32[H,W] roundtrip lossless. AT3: rgba uint8[H,W,4] roundtrip lossless. AT4: float16 downcast preserves precision. AT5: shape mismatch raises error. AT6: corrupt lz4 raises error. AT7: invalid channel name raises error. AT8: empty frame raises error. AT9: metadata JSON serializable.`

### 8.3 Key Contract Rules
- **Contract only at ST** (CoreAxiom_ContractOnlyAtST): SP/Spans never own Contracts directly.
- **Data type enforcement:** Contract data types are mandatory. This auto-resolves integration issues.
- **Single-file target:** Contract realization should target a single small file or adjacent implementation boundary near the context window (Axiom_ContractDescentTargetsSingleFileProjectionNearContextWindow).
- **Shared specification surface:** Contract is NOT a one-way derivation from ST. It is a shared specification surface between SemanticTwin and SourceCodeWorld. Both top-down (ST authors Contract) and bottom-up (SCW infers Contract) are valid.
- **Sole bottleneck:** The ONLY bottleneck in the entire APT methodology is Contract quality.

## 9. Relationship Types

| Relationship | Description |
|-------------|-------------|
| **DECOMPOSES_TO** | Span -> Span decomposition within SP world. N:N. Same-layer Spans are fully parallel. |
| **CRYSTALLIZES_TO** | AtomicSpan -> ST transition. The ONLY relationship that crosses the Crystallization Frontier. |
| **HAS_CONTRACT** | ST owns its Contract (I/O specification, type signature). Contract bridges ST and SourceCode. |
| **HAS_TASK** | ST owns its Task (TDD completion criteria, AcceptanceCriteria). Task PASS = Contract fulfilled. |
| **MATERIALIZES** | Contract -> actual SourceCode file/function implementation. Code is the Contract's materialization. |
| **INFORMED_BY** | Provenance tracking. Child Span -> INFORMED_BY -> parent Span or KG knowledge node. Tracks "what was referenced during creation." |
| **FULFILLS_REQUIREMENT** | Span or ST fulfills a specific Requirement. Created when linking from requirement queue to Span; Requirement status becomes fulfilled on completion. |

## 11. Architectural Molds (6 Molds)

APT defines 6 architectural molds that structure the tooling and operational surface:

### 11.1 Governance Mold
- **Tools:** Agent Instruction Profile, Hook and Approval Policy Engine
- **Role:** Controls command hooks, approvals, side-effect gates, tool policy enforcement. Unified instruction surface for repo rules and team conventions.
- **Flow:** STARTS_WITH -> APT Mold Usage Protocol; NEXT_MOLD -> Intent Mold

### 11.2 Intent Mold
- **Tools:** Requirement Graph, Span Planner Board
- **Role:** Graph-native requirement/intent model linking goals, constraints, acceptance criteria. Board for span decomposition, frontier readiness, blocked spans, sequencing.
- **Flow:** NEXT_MOLD -> Boundary Mold, Governance Mold

### 11.3 Boundary Mold
- **Tools:** Contract Registry, Twin Registry
- **Role:** Registry of typed contracts, invariants, versions, IO semantics. Tracks semantic twin lifecycle (draft -> crystallized -> implemented -> validated -> stale -> broken).
- **Flow:** NEXT_MOLD -> Execution Mold, Intent Mold

### 11.4 Execution Mold
- **Tools:** Semantic Work Queue Board, Subagent Router, Runtime Trace Graph
- **Role:** Queue of semantic work items with dependency/owner/priority/status. Routes spans and tasks to specialist subagents. Records actions, observations, tool calls as graph evidence.
- **Flow:** NEXT_MOLD -> Assurance Mold, Boundary Mold

### 11.5 Assurance Mold
- **Tools:** Eval and Review Harness
- **Role:** Combines automated checks, evaluator loops, review agents, merge-time bug finding.
- **Flow:** NEXT_MOLD -> (cycles back to Execution Mold)

### 11.6 Memory Mold (Cross-Cutting)
- **Tools:** Memory Tier Manager, Reflection Memory, Checkpoint and Replay Ledger
- **Role:** Manages working/graph/archive memory with retrieval, promotion, eviction. Stores failure lessons, retry notes, decomposition corrections. Stores checkpoints, replays, partial rollbacks.
- **Relationship:** CROSS_CUTS all other 5 molds (Governance, Intent, Boundary, Execution, Assurance)

## 12. Dual Guidance System

APT operates with two guidance modes:

| Mode | Where | Mechanism |
|------|-------|-----------|
| **Soft Guidance** | SP world (Spans) | Span descriptions, purposes, and KG knowledge links guide decomposition direction. Not enforced. |
| **Hard Guidance** | ST world (Contracts) + SCW (TDD) | Typed Contracts with data types, pre/post conditions, acceptance tests. TDD enforces compliance. Hallucination is structurally rejected by TDD. |

- **LLM = denoiser:** The LLM agent denoises ambiguity; APT structure serves as the context routing table.
- **Integration auto-resolved:** Enforced data types in Contracts automatically resolve integration issues between modules.

## 13. Bottom-Up (Ascent) Flow

APT supports bidirectional flow:

1. **Top-down (Descent):** SA -> SP -> ST -> SCW (standard flow)
2. **Bottom-up (Ascent):** SCW -> ST -> SP -> SA

### Bottom-up rules:
- Source code evidence is used first to restore/infer the shared Contract
- Contract is rebuilt, then SemanticTwin is reconstructed on top of it
- Only then does ascent continue toward SP -> SA
- The ascent maps source code meaning back to architecture (Axiom_BottomUpAscentMapsSourceCodeMeaningBackToArchitecture)

## 14. Clarification Notes (All 17)

These clarifications prevent common misreadings of the APT methodology:

### C1: Agent Methodology Is Refined By APT
Previous agent development methodologies must now be read through the APT lens. Prior contract-first or TDD-first descriptions are treated as partial tactics within the larger APT methodology.

### C2: AtomicSpan vs LeafSpan
LeafSpan = "currently has no child DECOMPOSES_TO" (a state; can be further decomposed). AtomicSpan = "judged to need no further decomposition" (must satisfy 4 crystallization criteria). Not all LeafSpans are AtomicSpans.

### C3: Bottom-Up Reconstructs Contract Then SemanticTwin
In bottom-up work, source code evidence first restores/infers the shared Contract, then SemanticTwin is rebuilt on that Contract, then ascent continues SP -> SA.

### C4: Contract Is Shared, Not One-Way Derived
"Contract derives from SemanticTwin" describes only the top-down perspective. Bottom-up can infer/restore the same Contract from SourceCodeWorld. The canonical Contract should be understood as a shared specification surface, not a one-directional derivation.

### C5: Contract Shared By Source And ST
SourceCodeWorld infers and materializes Contract; SemanticTwin is built on the same Contract + SemanticTask. Therefore Contract must exist both as Neo4j's canonical semantic contract AND as the source code's implementation-facing materialization.

### C6: Crystallization Frontier Is the Named SP-ST Boundary
The SP<->ST boundary now has an explicit name: Crystallization Frontier. When SP's AtomicSpan satisfies the 4 crystallization criteria, it reaches this frontier and proceeds to SemanticTwin authoring with shared Contract + SemanticTask.

### C7: Duplicate Synced Names Should Use Canonical Meaning
When synced glossary/howto/legacy nodes share the same name as canonical semantic concepts, canonical meaning must be read from the designated semantic concept node. Synced duplicate nodes are treated as aliases/views/legacy context.

### C8: Early Contract Descent Means Early Twinization
When one branch reaches sufficiency before its siblings, that branch can enter SemanticTwin authoring first. This does NOT mean SemanticPyramid directly owns Contracts (it never does).

### C9: KG Sparsity Caused Misread
Earlier insufficient KG descriptions made it possible to misinterpret that code-side SP/ST/SA were canonical or that Contract belonged to SP. This note records that the cause was KG description sparsity, not methodology intent.

### C10: L3 Contract Means Bridge Surface, Not Full Semantic Middle
Labels like "Contracts/Interfaces" usually refer to code-facing bridge surfaces around Contract. They do NOT mean the full semantic domain between SP and SCW, and do NOT include SemanticTwin or SemanticPyramid.

### C11: L3 Is Not Fixed AtomicSpan Layer
A project's AptSpans being AtomicSpans at L3 simply means that project's decomposition stopped at L3. L3 is NOT a fixed AtomicSpan layer. Other projects/branches may stop at L2 or descend to L7.

### C12: Legacy Contract-Centric Methods Are Partial Subsets
Existing contract-first, interface-driven, LX3 workflow nodes are still useful but must be read as partial tactics/preceding methods UNDER APT, not as complete replacements for SA, SP, ST, SCW.

### C13: Neo4j Canonicality
SA, SP, ST, Contract, SemanticTask are canonical semantic-layer objects in the Neo4j KG. Project source code is merely the implementation space. Code can materialize contracts, but code-side folders/helper models must NOT be confused with the semantic canon itself.

### C14: Span Is Not SP
Span is a planning-unit node within the SP (SemanticPyramid) world. SP is one world; Spans are its inhabitants. "Multiple SPs" is wrong -- it's "multiple Spans inside one SP." Do not conflate Span with SP.

### C15: Span Structure Is Layered Graph Not Tree
Spans need not form a tree. The key is that layers (L1, L2, ..., Ln) exist. Spans are graph nodes. External knowledge connects to Spans as graph relationships. Richer KG knowledge = stronger Span abstraction and code design capability.

### C16: Span-to-Contract Is Legacy Shorthand
Expressions like "span descends to contract," "contract-ready span," "early contract descent" are abbreviations only. SemanticPyramid NEVER directly owns Contracts. When the span frontier sufficiently closes, further pyramid descent stops and SemanticTwin authoring begins, where shared Contract + SemanticTask are specified before bridging to SourceCodeWorld.

### C17: TDD Verifies Contract Realization
TDD is primarily a discipline for verifying source code realization under explicit Contracts. Important in APT, but TDD itself is NOT SA, SP, or ST. It operates mainly at the Contract -> SourceCodeWorld realization stage.

### Insight: Plan As Upper Span
Work planning = building upper Spans. Sprint/Phase/SubPhase should be recursive decomposition of upper Spans, NOT separate execution layers.

## 15. Common Mistakes to Avoid (Error and Incident Notes)

### 15.1 APT Violation: PH3 -> PH5 Direct Jump
**Node:** `APT violation case: SM Serving Module PH3->PH5 direct`
**Description:** SM (Serving Module) L3 spans (6 total) were confirmed during PH3 (SP descent), then SKIPPED PH4 (ST crystallization) and jumped directly to PH5 (SourceCodeWorld) to write CLI/MCP/Viewer code.
**Lesson:** NEVER skip PH4. Every span must be crystallized into Contract + SemanticTask before writing code.

### 15.2 Asyncio Lock at Import Time
**Node:** `ERR_SM_AsyncioLockImportTime`
**Description:** `CameraService._lock = asyncio.Lock()` created at class definition time. CLI import without an event loop causes errors. Lock cannot be shared across event loops.

### 15.3 WebSocket Heartbeat Level Mismatch
**Node:** `ERR_SM_WS_HeartbeatLevel`
**Description:** Server expects app-level JSON ping; client uses WS-level ping only.

### 15.4 Register Format Mismatch
**Node:** `ERR_SM_WS_RegisterFormat`
**Description:** ReverseWSAgent register message format doesn't match PRISM server camera_ws.py expected format.

### 15.5 No Re-register After Connect
**Node:** `ERR_SM_NoReRegisterAfterConnect`
**Description:** `_rpc_connect()` succeeds in camera connection but doesn't re-register agent_id. If unknown at startup, stays permanently unknown.

### 15.6 File Transfer Error Handling
**Node:** `ERR_SM_FileTransferErrorHandling`
**Description:** `_send_file_binary()` missing WS None check, file I/O exception unhandled, chunk send failure not propagated.

### 15.7 Neo4j Wrong Port
**Node:** `ERR_SRV_Neo4jWrongPort`
**Description:** Neo4j bolt port 7687 (default) -> actual 55200. Both MongoDB settings and config_loader fallback needed correction.

### 15.8 SSH Tunnel CLOSE_WAIT Saturation
**Node:** `INC_SM_SSHTunnelCloseWait_20260316`
**Description:** Claude's parallel SSH sessions accumulated as CLOSE_WAIT zombies, saturating EdgeMan's reverse tunnel -> new SSH connections impossible.

### 15.9 Zivid XL250 CaptureAssistant Unsupported
**Node:** `ERR_SM_XL250_CaptureAssistant`
**Description:** Zivid 3 XL250 does not support CaptureAssistant (suggestSettings). ExposureTime max = 20000us.

## 17. Requirement Traceability

APT provides full requirement tracing through:
1. Requirements wait in a queue (SemanticWorkQueue)
2. Pulled from queue and linked to SP Spans (FULFILLS_REQUIREMENT)
3. Span crystallizes to ST -> Contract -> SourceCode
4. When complete, requirement moves to completed queue
5. RequirementSpan: special Span type for external requirements (can be added bottom-up)
6. This enables requirement traceability across the entire SA -> SP -> ST -> SCW pipeline
